# 学習ガイド品質チェック

## 読み手と構成

- 想定読者、事前知識、章の到達点を明示する。
- トップページから全章へ移動でき、各章からトップへ戻れる。
- 見出しは読者の疑問に答える文にする。製品名だけの見出しを連続させない。
- 1つの章では「概念 → 使いどころ → 構成 → 実践 → 確認 → 注意点」の順を基本にする。すべてが必要な場合だけ使う。
- 略語とCloudflare固有語は初出時に一文で説明する。似た製品の選定基準を併記する。

## 実践手順

操作を伴う説明には、必要な項目を次の形式で含める。

1. **事前準備**: アカウント、権限、ドメイン、課金の可能性、ローカル環境。
2. **手順**: 1操作ずつ実行できる順序。危険または課金につながる操作には注意を付ける。
3. **期待結果**: 実行後に画面、レスポンス、ログなどで何が見えるか。
4. **確認**: `curl`、DevTools、ダッシュボード、CLIなどで成否を判断する具体的方法。
5. **失敗時**: 代表的な症状、原因、最初に確認する場所。
6. **後片付け**: 検証用リソース、DNS、課金対象を残さないための作業。

コマンドはそのまま貼り付けて使えるようにし、プレースホルダーには意味と置換箇所を添える。出力例は成功と失敗を混同させない。

## 図と視覚表現

- リクエスト経路、選択フロー、責務分担、時間順の処理には図を検討する。
- 図の前後で「何を見る図か」「図から何を判断できるか」を説明する。
- 画像には内容が分かる代替テキストを付ける。装飾だけの画像は避ける。
- Mermaidは公開環境で確実に描画される構成がある場合だけ使う。そうでなければSVG/PNGまたはHTML/CSSの図を使う。

## HTML・レスポンシブ

- 正しい見出し階層、`nav`、`main`、リンク名、テーブル見出しを使う。
- 320px程度の狭い画面で、目次、コードブロック、表、画像が横幅を壊さないことを確認する。
- PCでは本文の最大幅を制限し、行が長くなりすぎないようにする。
- キーボードで目次とリンクを利用でき、フォーカスが見えることを確認する。
- 色だけで重要度や状態を伝えない。

## 公開前検証

- Markdownの内部リンクと画像パスを検査する。
- 実際のPagesビルド、または同等の静的サイトビルドを実行する。実行できない場合は理由を報告する。
- 主要ページをPC幅とSP幅でレンダリング確認する。
- 更新されやすい主張は公式Cloudflareドキュメントに照合し、未確認なら断定しない。
- 変更内容、実行した検証、未確認事項を分けて報告する。
